# Глубокий анализ репозитория `black_suite` и план внедрения AI/ML-оптимизатора

Дата: 2026-04-22

## 1) Что уже реализовано в репозитории

Проект уже содержит зрелый набор black-box подходов для дорогих внешних расчётов (COMSOL + `acli`) и разделяется на две ключевые ветки:

1. **Параметрическая оптимизация модели COMSOL** (в первую очередь через генетический алгоритм).
2. **Оптимизация формы** (через CMA-ES + подготовка границ смещений и параллельная оценка fitness).

Также есть отдельный градиентный (градиентоподобный) pipeline, утилиты LHS/датасета и UI для просмотра кэшей.

---

## 2) Архитектурная карта (по фактическому коду)

### Входные скрипты

- `comsol_optimization.rb` — основной запуск GA-оптимизации параметров COMSOL.
- `comsol_gradient_optimization.rb` — запуск многоточечного gradient-like поиска.
- `shape_optimization.rb` — запуск shape-оптимизации через CMA-ES.

### Конфиги

- `config.json`, `config_model_1.json`, `config_opt_bar.json` — сценарии параметрической оптимизации.
- `gradient_config.json` — настройки gradient pipeline.
- `templates/form_opt.json`, `templates/shift_boundaries.json` — шаблоны для `acli` задач.

### Основные Ruby-модули

- `src/optimization_config.rb` — валидация и доступ к конфигу GA/COMSOL.
- `src/genetics/comsol_genetic_optimizer.rb` — адаптивный GA с батч-оценкой, кэшем, диверсификацией.
- `src/genetics/gen_alg.rb`, `src/genetics/genetic_strategy.rb`, `src/genetics/individual.rb` — GA-ядро и стратегии.
- `src/optimization/cma_es.rb` — реализация CMA-ES (covariance adaptation, evolution paths, CSA).
- `src/form_optimization_fitness.rb`, `src/parallel_form_optimization_fitness.rb` — fitness для shape, в т.ч. параллельный.
- `src/boundary_shift_extractor.rb`, `src/shape_optimization_config.rb` — автоматизация подготовки shape-задачи.
- `src/optimization/gradient_descent.rb` — batch/multi-start градиентоподобный поиск.
- `src/problem.rb`, `src/runner.rb` — интеграция пакетного вызова COMSOL.

### Сервисный слой

- `tools/lhs.rb` — Latin Hypercube Sampling.
- `tools/dataset_builder.rb` — генерация параметрических батч-наборов.
- `ui/app.rb`, `ui/src/optimization_cache_dto.rb` — просмотр и агрегация исторических кэшей.

## 3) Детальное описание разработанных методов

## 3.1 Параметрическая оптимизация (GA + COMSOL)

Реализация: `src/genetics/comsol_genetic_optimizer.rb`.

### Что делает

- Генерирует начальную популяцию по диапазонам параметров (`mins/maxs`).
- Формирует батч-файл `batch_params.txt` и запускает один solver-run на группу точек.
- Читает результаты целевой функции из файла COMSOL.
- Применяет эволюционные шаги до сходимости/лимитов.

### Реализованные механизмы

- **Elitism** (сохранение лучших особей).
- **Адаптивный турнир** (размер турнира зависит от прогресса эпох).
- **Адаптивная мутация** при падении разнообразия.
- **Diversity-aware crossover**: если родители слишком похожи, генерируется «более далёкий» потомок.
- **Кэш вычислений fitness** (по округлённому ключу параметров), снижающий число дорогих вызовов COMSOL.
- **Early stopping по стагнации** через `epsilon + max_stagnant_epochs`.

### Практическая ценность

Для дорогих расчётов COMSOL такой дизайн минимизирует повторные вызовы solver-а и уменьшает риск преждевременной сходимости.

---

## 3.2 Shape optimization через CMA-ES

Реализация: `shape_optimization.rb`, `src/optimization/cma_es.rb`, `src/boundary_shift_extractor.rb`.

### Pipeline

1. Получение допустимых диапазонов смещений: `acli bs-shift-boundary`.
2. Чтение `shifts.txt` и формирование задачи в размерности `N`.
3. CMA-ES в нормализованном пространстве [0,1].
4. Для каждого кандидата: генерация коэффициентов → `acli bs-form-opt` → чтение цели.

### Реализованные элементы CMA-ES

- Взвешенная рекомбинация лучших особей ($\mu$-recombination).
- Адаптация ковариационной матрицы (rank-one + rank-$\mu$ updates).
- Эволюционные пути (`p_sigma`, `p_c`).
- CSA step-size adaptation.
- Собственное разложение ковариации (Jacobi-based) для трансформации сэмплов.
- Пакетная оценка популяции (если fitness поддерживает `evaluate_batch`).

### Практическая ценность

Подходит для высокоразмерных непрерывных задач формы, где производные недоступны/шумные.

---

## 3.3 Параллельная оценка fitness для shape

Реализация: `src/parallel_form_optimization_fitness.rb`.

### Ключевая инженерная идея

- Каждая оценка уходит в **отдельную worker-директорию**, что снижает конфликты по файлам.
- Поддерживаются особенности Windows file-locking (`wait_for_file_unlocked`).
- Несколько процессов `acli` запускаются параллельно батчами по `max_workers`.

### Практическая ценность

Резко снижает wall-clock time при дорогом fitness.

---

## 3.4 Multi-start gradient-like метод

Реализация: `src/optimization/gradient_descent.rb`.

### Что делает

- Генерирует несколько стартовых точек.
- Оценивает батчем через COMSOL.
- Для лучших точек строит локальные окрестности (комбинаторика смещений по координатам).
- Адаптирует скорость шага и сохраняет улучшения.
- Использует кэш по сигнатуре точки.

### Важный нюанс

Это не классический строгий градиентный спуск, а скорее **агрессивный локально-поисковый метод** с пакетной оценкой и memory/cache.

## 4) Сильные стороны текущего решения

1. Готовая промышленная интеграция с COMSOL/`acli`.
2. Батч-вычисления и кэширование — критично для дорогих задач.
3. Два класса оптимизации: параметры и форма.
4. Параллельный pipeline для shape-оценки.
5. Наличие LHS и исторических кэшей для последующего ML.

---

## 5) Основные ограничения и технический долг

1. Нет единого abstraction-слоя «Optimizer API» для легкого переключения метода.
2. Нет мета-оптимизатора, выбирающего стратегию по этапам/бюджету.
3. Нет surrogate-based Bayesian/AI-ветки в прод-контуре.
4. Ограниченная воспроизводимость (не везде seed/протоколы экспериментов зафиксированы).
5. Неполная унификация формата логов/результатов между pipeline-ами.

## 6) План внедрения альтернативного оптимизатора на основе современного AI/ML

Ниже практичный, поэтапный roadmap с минимальным риском и максимальной повторной использованием текущего кода.

## 6.1 Целевая концепция (гибрид)

**Рекомендуемая стратегия: Hybrid AI Optimizer**

- Этап A (exploration): LHS + существующий GA/CMA-ES для первичного покрытия пространства.
- Этап B (surrogate learning): обучение surrogate-модели $\hat{f}(x)$ на накопленных данных.
- Этап C (acquisition): выбор следующего батча кандидатов через BO/аквизицию.
- Этап D (trust-region local refine): локальное уточнение лучшего решения (CMA-ES или local search).
- Этап E (active learning loop): итеративное дообучение суррогата и продолжение поиска.

---

## 6.2 Что внедрять в первую очередь (параметрическая задача)

Параметрические задачи (3–10D) — лучший старт для AI, потому что:

- уже есть кэши параметр→fitness,
- меньше размерность,
- быстрее набирается обучающая выборка.

### Минимально жизнеспособный AI-модуль (MVP)

1. Собираем датасет из существующих `optimization_cache_*.json`.
2. Учим surrogate (на старте: `Gaussian Process` или `XGBoost`-регрессор).
3. Выбираем кандидатов по acquisition (Expected Improvement / UCB).
4. Оцениваем кандидатов реальным COMSOL.
5. Добавляем результаты в датасет и повторяем цикл.

---

## 6.3 Рекомендуемая архитектура классов (Ruby-first)

## 6.4 Математика выбора кандидатов (кратко)

Для минимизации можно начать с Expected Improvement:

$$
EI(x) = \mathbb{E}[\max(0, f_{best} - f(x))]
$$

где распределение $f(x)$ даёт surrogate (например, GP с предсказанием среднего и дисперсии).

Если uncertainty-оценка у модели отсутствует (например, обычный GBM), можно использовать ансамбль моделей и эмпирическую дисперсию как proxy.

## 6.5 Пошаговый roadmap внедрения

## Phase 1 (1–2 недели): Data & Infra

1. Нормализовать формат экспортируемых результатов из всех оптимизаторов.
2. Реализовать `SurrogateDataset`:
   - импорт старых кэшей,
   - валидация размерности и диапазонов,
   - train/val split,
   - версионирование датасета.
3. Добавить `experiment_tracker` (seed, конфиг, бюджет, метрики).

**Критерий готовности:** воспроизводимый датасет + единый формат экспериментов.

## Phase 2 (2–3 недели): Parametric AI Optimizer MVP

1. Реализовать `HybridAIOptimizer` для параметрических задач.
2. Вариант 1: GP surrogate + EI/UCB.
3. Вариант 2 (fallback): ансамбль деревьев + uncertainty proxy.
4. Интегрировать батч-кандидаты в существующий COMSOL batch-runner.

**Критерий готовности:** за одинаковый бюджет вызовов COMSOL получить улучшение относительно baseline GA минимум в части задач.

## Phase 3 (2 недели): Hybrid orchestration

1. Добавить режимы запуска:
   - `ga_only`, `ai_only`, `hybrid_ga_ai`, `cma_ai`.
2. Реализовать policy переключения фаз (explore/exploit/trust-region).
3. Добавить restart-логику при стагнации суррогата.

**Критерий готовности:** стабильные прогоны без деградации на «сложных» задачах.

## Phase 4 (2–4 недели): Shape + AI

1. Применить surrogate к shape-задаче (с батч-стратегией).
2. Рассмотреть редукцию размерности (PCA/autoencoder) перед surrogate.
3. Оставить CMA-ES как локальный уточнитель в trust-region.

**Критерий готовности:** снижение числа дорогих `acli bs-form-opt` вызовов при том же качестве.

## 6.6 Метрики успеха

Сравнение с baseline (GA/CMA-ES) по одинаковому compute budget:

1. Лучшее значение цели за $N$ вызовов симулятора.
2. Время до достижения target-fitness.
3. Количество симуляций до target-fitness.
4. Стабильность (дисперсия результата по seed).
5. Стоимость одной «полезной» итерации (wall-clock + solver time).

---

## 6.7 Практический стартовый сценарий (рекомендуется)

1. Взять `config.json` (3 параметра: `c1,c2,c3`) как pilot-case.
2. Поднять baseline:
   - GA (текущий),
   - gradient-like (текущий).
3. Обучить первый surrogate на исторических кэшах + LHS-добавке.
4. Запустить AI-loop на 30–50 новых вызовов COMSOL.
5. Сравнить с baseline по равному бюджету.

---

## 6.8 Риски и как их снизить

1. **Шум/нестабильность solver-а** → использовать robust-метрики и повторные оценки топ-кандидатов.
2. **Мало данных для surrogate** → старт с LHS + transfer из кэшей прошлых прогонов.
3. **Переобучение surrogate** → cross-validation + uncertainty-aware acquisition.
4. **Высокая размерность shape** → редукция размерности + trust-region.
5. **Сложность поддержки** → сохранить единый Ruby API и прозрачные конфиги.

## 8) Вывод

Проект уже содержит сильный инженерный фундамент: интеграция с solver-ами, батч-вычисления, кэш, параллелизм и два класса оптимизации (параметры/форма). Наиболее рациональный путь внедрения современного AI — **гибридный параметрический MVP** (surrogate + acquisition + реальная симуляция в цикле), после чего масштабирование на shape-задачи через trust-region и размерностную редукцию.

Итоговая рекомендация: **не заменять существующие методы, а оркестрировать их** — GA/CMA-ES как надёжные baseline/refinement, AI-суррогат как ускоритель поиска по дорогой чёрной коробке.
